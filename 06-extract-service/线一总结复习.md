## 二、全链路架构图（背下来）

```
JavaClientDemo.java          server.py (FastAPI, 8300)        extractor.py                Claude API
【Java 后台】      ──HTTP──→ 【AI 服务】            ──SDK──→  【提取器】        ──HTTPS──→ 【模型】
盔甲: 超时5s/32s              兜底: try/except                 盔甲: 超时30s+重试×3
     重试×3+指数退避              返回 {"ok":false}                指数退避1s→2s→4s
     降级人话文案                                                  429 读 retry-after
```

**盔甲分布铁律**：每一跳都有超时；同一个失败只在"直接调下游"的那一层重试。

### 步骤 1 · git 建仓与推送（Git 闯关 1/4/6 关实战版）

学到的命令链（以后天天用）：

```bash
git init -b main              # -b main：指定主分支名（GitHub 默认 main，别再用老默认 master）
git add -A                    # 全部改动进购物车
git commit -m "说明"
git remote add origin git@github.com:Clara-Doctor/studyAi.git   # 绑远程（一次）
git push -u origin main       # 首推（-u 建立绑定，以后裸 push 即可）
```

- **认证走的 SSH 钥匙**：`~/.ssh/id_ed25519_github` → 推送全程没弹登录框。
  凭据管理器是 HTTPS 的玩法，SSH 是钥匙对的玩法——两套体系互不相干
- **.gitignore 实战**：`__pycache__/`、`.env`、`*.log` 在首次 add 前就写好——
  所以垃圾文件从没进过仓库（`git status` 里看不到它们就是证据）
- **LF/CRLF 警告**：Windows 换行符转换提示，无害，忽略

### 步骤 2 · 生产盔甲（教程第 7 章落地）⭐ 本线核心

**错误分类学**（重试的灵魂，背下来）：

| 错误 | 重试？ | 原因 |
|---|---|---|
| 429 限流 / 5xx / 超时 / 断连 | ✅ 指数退避重试 | 对方/网络的问题，再试可能就好 |
| 400/401 参数错 | ❌ 立刻抛 | 自己的问题，重试一万次也是错 |

`call_with_retry` 的结构（三行核心）：

```python
for attempt in range(max_retries + 1):
    try:    return make_request()            # 正常就返回
    except (可重试错误):  wait = 退避节奏或 retry-after; sleep(wait)
    # 不可重试错误 → 直接 raise
```

- 包装手法：`call_with_retry(lambda: client.messages.create(...))` ——
  **把"发请求那行"塞进 lambda，业务代码一个字没动**
- **验证军规**：改完立刻跑 `eval.py`，87% 与基线一致 → 证明盔甲零破坏。
  （朝向 44%→39% 是模型随机性波动，不是破坏——分项波动看趋势不看单次）

### 步骤 3 · FastAPI 服务化（20 行核心知识）

```python
app = FastAPI(title="房源提取服务")            # 应用对象

class ExtractRequest(BaseModel):               # 请求体格式（pydantic 在接口边界校验）
    text: str

@app.get("/")                                  # GET 接口：健康检查
def health(): return {"status": "ok"}

@app.post("/extract")                          # POST 接口：核心业务
def extract(req: ExtractRequest):
    try:
        listing = extract_listing(req.text)    # 复用旧代码——服务化≠重写
        return {"ok": True, "data": listing.model_dump()}
    except Exception as e:                     # 服务永不抛堆栈给调用方
        return {"ok": False, "error": str(e)}
```

- **复用手法**：`sys.path.insert(0, 兄弟项目路径)` → `from extractor import extract_listing`
  ——02 里的业务代码原样变成 06 服务的引擎
- 启动：`python -X utf8 -m uvicorn server:app --port 8300`

### 步骤 4 · 实测与一个真实的坑

- `curl -d @body.json` **必须用文件传中文 body**：Git Bash 控制台是 GBK，
  命令行里直接写中文 JSON 会发出去乱码字节，FastAPI 报 "error parsing the body"
  【踩坑实录：第一次调用就是这么挂的，换文件方式立刻好】
- 健康检查先行：`curl http://127.0.0.1:8300/`——先证明服务活着，再调试业务接口

### 步骤 5 · Java 调用方（JDK 17）

- **JDK 版本决定写法**：JDK 8 只有 `HttpURLConnection`（老式繁琐）；
  JDK 11+ 才有现代 `HttpClient`——你机器 PATH 默认 8，真身在
  `E:\env\jdk-17.0.20.1+1`（还有 `C:\Program Files\Eclipse Adoptium` 双 JDK 并存）
- Java 版盔甲三件套：`HttpClient.connectTimeout(5s)` + `HttpRequest.timeout(32s)`
  （读超时故意比服务端内部 30s 略大）+ 重试循环里 `1L << attempt` 指数退避
- **错误分类学的 Java 版**：`code==429 || code>=500 → 抛 Retryable`；
  `code>=400 → 直接返回说明不重试`——和 Python 版一模一样的逻辑，换个语言
- **降级**：重试用尽 `return "{\"ok\":false,\"error\":\"服务暂不可用，请稍后再试\"}"`
  ——给人话，不给堆栈
- **对应关系**（工作里写 Spring 时）：手写的三个方法 ≈ resilience4j 的三个注解
  `@Retry / @TimeLimiter / @RateLimiter`

### 步骤 6 · 全链路验收（三条样例的解读）

| 输入 | 返回 | 解读 |
|---|---|---|
| 两室一厅89平朝南月租3200停车方便 | 5 字段全出 ✅ | 干净用例，标准路径 |
| 南北通透三居室145平精装修租金9000元每月 | parking=null ✅ | 没提车位 → null（纪律） |
| 小区环境好拎包入住 | 全 null（JDK17 轮）/ 部分未知（JDK11 轮） | **同一输入两次结果不同 = 模型随机性**；null 是对的（MISSIONS 第 2 关要修的活），服务层忠实转发不背锅 |

**一个重要观察**：服务层（server/Java）对模型输出的错误**照单转发**——
盔甲只保护"链路"，不保护"质量"。质量由评测（eval.py）和提示词手术管，
**链路可靠 ≠ 内容正确**，这是两层完全不同的工程。
