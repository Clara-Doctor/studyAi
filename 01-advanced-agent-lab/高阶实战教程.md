## 第 1 课：最小可运行 Agent —— 亲眼看循环

**文件**：`01_minimal_agent.py`

跑完后回头看输出，你会看到类似：

```
========== 第 1 轮 ==========
stop_reason = tool_use
AI 想用工具 -> read_file，参数 = {'path': 'README.md'}
工具返回 -> # 高阶实战实验室...
========== 第 2 轮 ==========
stop_reason = end_turn
```

**这就是 Agent 的完整一生**：模型说"我要读文件"（`tool_use`）→ 我们执行并把结果喂回 → 模型消化后说"做完了"（`end_turn`）。

三个必须刻进脑子的细节：

1. **`messages.append({"role": "assistant", "content": response.content})` 不能漏**——模型自己的回复（包括工具调用请求）必须回填对话历史，否则下一轮 API 直接报错。
2. **`tool_use_id` 必须和 `tool_use` 的 id 对应**——模型靠 id 把"我点的菜"和"端上来的菜"配对。
3. **模型从不动手，它只点名**——`read_file` 是不是真的读了文件，完全取决于你的 `execute_tool` 写了什么。你可以让它读文件时"作恶"（返回错误内容），模型就会被骗——这就是后面安全课的伏笔。

**练习 1.1**：把任务改成"README.md 里出现了几次 'Agent' 这个词？"，观察它是否需要重新读文件。
**练习 1.2**（重要）：给 `read_file` 故意传一个不存在的路径场景——把 `execute_tool` 改成永远返回 `"错误：文件不存在"`，看模型如何反应（它会报告失败而不是胡编内容）。

## 第 2 课：给 Agent 装工具箱

**文件**：`02_toolbox.py`

新增三个工程手法：

1. **工具分发表**：`TOOL_HANDLERS = {"list_files": tool_list_files, ...}`。加新工具 = 加一个函数 + 表里加一行 + TOOLS 里加一段定义。三处改动，一目了然。
2. **错误也是一种结果**：工具失败时不抛异常，而是返回 `(错误信息, is_error=True)`。模型收到错误后会**自己换思路**（比如换个路径、先 list 再 read）——这就是 Agent 的"韧性"来源。
3. **多步任务自主规划**：任务只说"看看 docs、写 summary.md"，没说先做什么。观察它自己排出：list → read×3 → write → 总结 的顺序。

**练习 2.1**：加第 4 个工具 `delete_file`（照抄 write_file 改一下），让 Agent "删除 docs/summary.md"。
**练习 2.2**（思考题）：delete 是危险操作。如果这是真实系统，你会怎么防误删？（提示：在 `execute_tool` 里加人工确认，或者干脆不提供这个工具——"能力最小化"是 Agent 安全的第一原则。）

## 第 3 课：健壮性 —— 把循环封装成框架

**文件**：`agent_lib.py`（本课产物，后面所有课都依赖它）

对比第 1 课，`run_agent()` 多了五样东西，每个都是生产级必备：

| 增强 | 为什么必须有 |
|---|---|
| `system_prompt` 参数 | 设定身份和规矩，比如"操作简洁"能省大量输出 token |
| `max_turns` 上限 | 模型可能陷入死循环（反复读同一个文件），不设上限就是无底洞的账单 |
| 统一处理 `stop_reason` | `refusal`（模型拒绝）、`max_tokens`（输出被截断）都要处理，不能只认 `end_turn` |
| `tool_executor` 可替换 | 想给主 Agent 挂"特殊工具"（如第 7 课的 delegate）时不用改框架——**依赖注入** |
| 路径安全防护 `_resolve()` | 模型输出是不可信输入！如果模型传 `../../重要文件`，没有防护就会读/写到目录外。**路径穿越是最常见的 Agent 安全漏洞** |

跑一下自测：`python agent_lib.py`

**练习 3.1**：试试绕过防护——手动构造一个请求让 Agent 写 `../escape.txt`，确认被拒绝。
**练习 3.2**：把 `max_turns` 改成 2 跑一遍，观察"强制结束"分支。

到这里，你已经拥有一个 60 行左右的迷你 Agent 框架。**Claude Code 的本质 = 这个循环 + 几十个精心打磨的工具 + 上下文管理 + 权限系统。**

## 第 4 课：流式输出 + 结构化输出

**文件**：`04_streaming_structured.py`

**流式（streaming）**：长输出如果一次性等完，容易撞上 HTTP 超时；流式让内容边生成边到达。记住 `stream.get_final_message()`——流完仍能拿到完整消息对象，两全其美。

**结构化输出（structured output）**：传统方式模型返回一段话，你用正则/字符串去抠信息，脆弱得很。结构化输出让模型直接按 Pydantic 模型返回，拿到的是**类型安全的 Python 对象**，可以 `if review.severity == "high"` 这样编程处理。

这是第 6 课的关键前置：**评审者的结论必须是结构化的**（`verdict: pass/revise`），主循环才能用代码判断走向——总不能让程序去读"我觉得还行吧"。

**练习 4.1**：给 `CodeReview` 加一个 `suggested_fix: str` 字段，重跑。
**练习 4.2**：故意让 schema 里有个模型无法满足的字段（比如要求输出 5 段代码），观察行为，体会 schema 设计要合理。

## 第 5 课：上下文工程（无代码文件，改 agent_lib 做实验）

上下文是 Agent 最稀缺的资源。三个立刻能用的技术：

### 5.1 先学会"看见"上下文有多大

```python
resp = client.messages.count_tokens(
    model=MODEL,
    messages=[{"role": "user", "content": open("docs/auth.md", encoding="utf-8").read()}],
)
print(resp.input_tokens)   # 中文文档 1 个字 ≈ 1~2 token
```

### 5.2 压缩（compaction 的手工版）

对话滚了几十轮后，早期细节已经没用了。在 `run_agent` 里加一个触发器：

```python
# 放在 run_agent 的循环里，每轮开始前检查
if len(messages) > 30:  # 轮数阈值，自己调
    summary = client.messages.create(
        model=MODEL, max_tokens=2000,
        messages=[{"role": "user", "content":
            "把下面的对话历史压缩成要点清单，保留：当前任务、已完成的事、关键决定。丢掉过程细节。\n\n"
            + str(messages)}],
    ).content[0].text
    messages = [{"role": "user", "content": f"[此前对话摘要]\n{summary}"}]
```

原则：**上下文里只留"会影响下一步决策的信息"**。Claude Code 里对应的就是 `/compact` 和 `/clear`。

### 5.3 跨会话记忆 = 一个文件

Agent 的"记忆"不需要数据库，一个 markdown 文件就够了：

```python
MEMORY = BASE_DIR / "agent_memory.md"
# 任务开始时：如果存在，把内容注入 system prompt
# 任务结束时：让 Agent 把"这次学到的经验"追加进去
```

**练习 5.1**：实现 5.2 的压缩逻辑，用长任务测试（让 Agent 总结 3 份 docs 文档并多轮追问）。
**练习 5.2**：实现记忆文件，跑两次同一任务，第二次观察它是否"记得"上次的产出。

## 第 6 课：双 Agent 对抗（生成者 vs 评审者）

**文件**：`05_generator_critic.py`

跑之前先想一个问题：**为什么不让生成者自己检查自己？**

因为生成者的上下文里装满了"我为什么这么写"的理由——它有沉没成本，有立场。评审者运行在**全新上下文**，只看到规格和代码，没有历史包袱，所以挑得出真问题。这就是 Judge/Critic 模式的全部原理。

跑的时候注意三个结构设计：

1. **打回是结构化的**：`Verdict(verdict, issues)`——主循环用 `if v.verdict == "pass"` 判断，issues 直接拼进下一轮生成者的任务里。全靠第 4 课的结构化输出。
2. **对抗有上限**：`range(1, 4)` 最多 3 轮。无上限的"打回-修改"循环会永远吵下去，且每轮都在烧钱。**到上限就升级给人**，这是正确的产品设计。
3. **生成和评审用的 system prompt 完全不同**：一个是"严谨工程师"，一个是"极挑剔的评审员"。多智能体的"分工"，很大程度就是不同的 system prompt + 不同的上下文。

**练习 6.1**：把规格改得更刁钻（比如"必须处理 nums 含 NaN 的情况"），看几轮能过。
**练习 6.2**：让评审者也看生成者的自测代码，对比打回率变化。

## 第 7 课：指挥官-工人（本课程的高潮）

**文件**：`06_orchestrator_worker.py`

核心技巧只有一行话：**把"派子智能体"本身注册成一个工具**。

```python
DELEGATE_TOOL = {
    "name": "delegate",
    "description": "把一个独立的调研子任务交给子智能体执行……",
    ...
}

def delegate(task: str) -> str:
    # 每次 delegate = run_agent() 全新启动 = 全新上下文
    return run_agent(EXPLORER_SYSTEM, task, tools=FS_TOOLS, verbose=False)
```

对主 Agent 来说，`delegate` 和 `read_file` 没有任何区别——都是"点名 → 拿到返回值"。但它的返回值背后，是一个完整的子 Agent 跑完了几十轮工具调用。**这就是 Claude Code 里 Agent 工具的原理，也是所有多智能体框架的地基。**

跑完后回答三个观察题：

1. 主 Agent 是不是在一轮里同时发了多个 `delegate`？（并行——API 允许一次响应带多个 tool_use，我们第 1 课的循环天然支持）
2. 子智能体返回的是"结论"还是"过程"？主 Agent 的上下文里因此多了多少内容？
3. 假如不用子智能体，让主 Agent 自己读完 3 份文档再写报告——它上下文里会多出什么？哪个方案更适合"调研 300 份文档"的场景？

**练习 7.1**：把 docs/ 扩充到 5 份文档，观察并行委派的效果。
**练习 7.2**（进阶）：给 delegate 加 `worker_type` 参数，支持两种工人：`explorer`（调研）和 `critic`（评审）。这已经是"按需组建团队"了。

## 第 8 课：评测 —— 让改进可度量

**文件**：`07_eval.py`

没有评测的 Agent 开发 = 蒙眼开车。改了 prompt "感觉好点了"？到底好了多少？换个便宜模型会掉分吗？只有评测集能回答。

两种评测形态，覆盖两类任务：

- **Part A 单次调用评测**：6 个固定分类用例 + 标准答案 → 算准确率。判分是确定性的（字符串相等），不花一分钱评审费。
- **Part B Agent 行为评测**：判分标准不是"回答好不好听"，而是**事有没有真的做成**——文件必须真实存在、标题格式必须合格。这教的是最重要的 mindset：**验收 Agent 靠检查产物，不靠感觉**。

**练习 8.1**：把 `CLASSIFICATION_CASES` 扩到 15 条，故意加几条刁钻的（反讽、混合情感）。
**练习 8.2**：跑一遍记录分数 → 把 `agent_lib.py` 的 `MODEL` 换一个模型 → 再跑对比。你刚刚完成了一次正经的"模型选型评测"。
**练习 8.3**：给 Part B 加第三个检查："3 条任务里至少有 1 条以 `-` 开头"（列表格式检查）。

## 第 9 课：Claude Code 里的高阶玩法（不用写代码）

前 8 课你造了轮子；这课用现成的轮子武装你的日常开发。以下配置放到**任意项目根目录**的 `.claude/` 下即可生效。

### 9.1 自定义子智能体（相当于你写的 delegate 工具）

创建 `.claude/agents/code-reviewer.md`：

```markdown
---
name: code-reviewer
description: 资深代码评审员。写完功能或修完 bug 后主动使用。
tools: Read, Grep, Glob, Bash
---
你是资深代码评审员。审查代码时按优先级只报告确定的问题：
1. 正确性 Bug（会算错的、会崩的）
2. 安全问题（路径穿越、注入、越权）
3. 与项目现有模式的不一致
每条问题附 文件:行号 和一句话修复建议。没有问题就明说"未发现问题"。
```

之后你在 Claude Code 里说"让 code-reviewer 审一下我刚写的模块"即可。**它拥有独立上下文**——和你第 6 课的评审者一样。

### 9.2 自定义 Skill（把重复流程变成自动加载的手册）

创建 `.claude/skills/release-notes/SKILL.md`：

```markdown
---
name: release-notes
description: 需要生成发版说明（changelog）时使用。根据 git log 整理用户视角的更新摘要。
---
生成发版说明的流程：
1. 运行 git log --oneline 上个 tag..HEAD 获取提交
2. 按类型分组：新功能 / 修复 / 破坏性变更
3. 忽略 "chore"、"typo" 类提交
4. 输出到 CHANGELOG.draft.md，语言用用户视角（"现在可以…"而不是"重构了…"）
```

平时只占一行描述；你说"帮我写下个版本的发版说明"时它才全文加载——这就是渐进式披露。

### 9.3 Hook：在特定时机自动执行

创建/编辑 `.claude/settings.json`：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "echo [hook] 文件刚被修改" }
        ]
      }
    ]
  }
}
```

真实用途示例：每次 AI 改完代码自动跑 `ruff format`、自动跑测试、敏感文件被改时告警。Hook 是**确定性**保障——不依赖模型"记得"做。

### 9.4 MCP：接入外部服务

```bash
claude mcp add --transport http github https://api.githubcopilot.com/mcp/
claude mcp list
```

装好后直接对 Claude Code 说"列出我仓库最近的 5 个 open PR 并总结"。

### 9.5 并行子智能体的日常用法

不写任何配置，直接这样说：

> 并行派 3 个子智能体，分别调研 src/ 下 auth、billing、orders 三个目录的职责和潜在问题，汇总给我。

体会它和你第 7 课写的代码一一对应的关系。

## 第 10 课：毕业项目 —— 代码库体检机器人

把整门课的组件拼成一个真实工具：**输入任意一个项目文件夹，产出一份《体检报告》**。

```
输入：某个项目路径
流程：
  1. 主 Agent 列出目录结构，拆出 3~6 个模块
  2. 并行 delegate 给 explorer 子智能体：逐模块调研（职责、入口、依赖）
  3. delegate 给 critic 子智能体：评审汇总草稿，挑事实错误
  4. 主 Agent 修订，写出 final_report.md
验收（用第 8 课的思路写自动判分）：
  - 报告文件存在
  - 报告覆盖了所有列出的模块（字符串检查）
  - 报告无"TODO/待补充"字样
```

**里程碑**：
- M1：跑通"列目录 → 派 1 个 explorer → 收到结论"（第 3+7 课）
- M2：并行多 explorer + 汇总写文件（第 7 课）
- M3：加入 critic 评审环节（第 6 课）
- M4：写 eval 脚本验证产物质量（第 8 课）

做完这个项目，你已经具备搭建生产级 Agent 系统的全部核心能力。

## 附：新手最容易踩的 8 个坑

1. **忘记 append 模型的 assistant 回复** → 下一轮 API 报错
2. **`tool_use_id` 对不上** → API 报错，检查是否逐个 block 对应
3. **不设 `max_turns`** → 模型死循环，账单起飞
4. **`max_tokens` 给太小** → 输出（含思考）被截断，`stop_reason=max_tokens`
5. **工具 description 写得太含糊** → 模型乱调工具或编造工具名；description 要写清"什么时候用、参数是什么"
6. **直接 `open(模型给的路径)`** → 路径穿越漏洞，务必像 `_resolve()` 一样约束在白名单目录内
7. **让上下文无限膨胀** → 记得压缩/清场，"只留影响下一步决策的信息"
8. **相信"我觉得变好了"** → 一切改动过评测集，用分数说话
