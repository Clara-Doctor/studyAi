# SPEC：房源信息提取器 · 评测闯关练习项目

> 目的：通过把一个"故意只有约 60 分"的房源提取器亲手修到 95 分以上，
> 完整体验第 7 课教的"评测驱动开发"循环：基线 → 改进 → 重跑对比 → 扩充回归。

## 1. 被评测的产品（extractor.py）

输入：一段口语化中文房源描述。
输出：5 个结构化字段（pydantic 模型 `Listing`，结构化输出方式与课程第 7 课 Part A 相同）。

| 字段 | 类型 | 归一化规则（标准答案和判分都按这个约定） | 对应难点 |
|---|---|---|---|
| `layout` | str/null | 统一格式 `"N室N厅"`（阿拉伯数字），如 "两室一厅"→"2室1厅"；未提及 → null | 写法多变 → 输出格式约定 |
| `area` | number/null | 纯数字（平方米），"89平"/"89㎡"/"89平米" → 89；未提及 → null | 单位噪声 → 剥离单位 |
| `price` | number/null | 纯数字（月租，元），"3.2k" → 3200；未提及 → null | 缩写换算 → 少见写法规则 |
| `orientation` | str/null | 枚举：`东`/`南`/`西`/`北`/`南北`；"南北通透"→"南北"，"朝南"→"南"；未提及 → null | 返回不稳定 → 枚举约束 |
| `parking` | bool/null | 明确说有车位/可停车 → true；明确说没有 → false；**没提 → null（不许猜）** | 幻觉 → 三值规则 |

null 语义：**"描述里没提到"必须返回 null**——这是全项目最重要的教学点（模型不许编造）。

## 2. 用例集（cases.json）

18 条固定用例，格式：

```json
{"text": "朝阳公园附近两室一厅，89平朝南，月租3200，小区停车方便",
 "answer": {"layout": "2室1厅", "area": 89, "price": 3200, "orientation": "南", "parking": true}}
```

覆盖矩阵（每条用例可覆盖多类）：
- 4 条干净写法（标准格式，v1 也应能对——保证基线不为 0）
- 4 条中文数字户型（两室一厅 / 三室两厅…）
- 3 条面积单位变体（㎡ / 平米 / 平）
- 2 条价格缩写（"3.2k" 型，需换算成 3200；不收"三千二"型中文数字价格，超出范围）
- 2 条朝向变体（南北通透 / 朝南）
- 3 条字段缺失（parking 未提 / price 未提 / 多字段未提）
- 1 条极端用例：全字段缺失（"小区环境好，拎包入住"→ 全 null）

【铁律】用例一旦建立就是"标尺"，改进阶段**不许改**；第 3 关只准**追加**新用例。

## 3. 判分器（eval.py）

- 逐条调用 `extractor.extract_listing()`（从 extractor 导入，避免两处定义模型）
- **先归一化再比对**（与标准答案同规则）：layout 正则提取 `(\d+)室(\d+)厅`；
  area/price 转 float 容差 0.01；orientation 精确比对；parking 布尔比对
- 计分粒度：**字段级**。每条用例 5 个字段，每字段 1 分
- 报告输出：
  1. 总体字段准确率：`对的字段数 / (18×5)`
  2. 分项准确率：每个字段单独的百分比（定位最弱字段）
  3. 错题清单：`期望=? 实际=? | 用例文本`（仅打印错的部分）
- 健壮性：单条 API 调用失败重试 1 次，仍失败则该条记 0 分并标注"API错误"，
  **不中断整场评测**

## 4. extractor v1 的"埋坑清单"（故意缺陷 = 第 2 关要修的东西）

v1 提示词故意只写一句模糊的"你是房源信息提取助手，提取户型/面积/租金/朝向/车位，返回 JSON"，
不解释任何格式约定。预期基线 **55%~75%**（干净用例能对，难的挂）：

| # | 坑 | 挂掉的字段 | 第 2 关的解法（提示词技巧） |
|---|---|---|---|
| 1 | 无格式约定 → 返回"两室一厅" | layout | 明确输出格式 "N室N厅" |
| 2 | 未说剥离单位 → 返回 "89平米" | area | 只要数值，单位剥离 |
| 3 | 未说缩写换算 → "3.2k" 提错 | price | 补充少见写法规则 |
| 4 | 无枚举约束 → "朝南"/"south" | orientation | 枚举白名单 |
| 5 | 无 null 规则 → 没提车位时瞎猜 | parking | 三值规则 + "不知道就 null" |

## 5. 关卡设计（MISSIONS.md）

| 关 | 任务 | 规则 | 验收标准 |
|---|---|---|---|
| 1 建立基线 | 跑 eval.py，记录分数，读懂分项报告和错题清单 | 只观察，不改 | 能说出 5 个字段各自失分原因 |
| 2 提示词手术 | 迭代 extractor.py 的 SYSTEM_PROMPT | **只准改提示词**，不准动 cases.json / eval.py | 连跑 2 次字段准确率都 ≥95%（测稳定性） |
| 3 扩充回归 | 自写 ≥2 条新描述 + 人工标注答案，追加进 cases.json | 只准追加，不准改旧用例 | 总用例 ≥20 条且重跑仍 ≥95%；挂了就继续迭代 |

每关附思考题（延续课程风格）。所有代码零基础中文注释。

## 7. 环境

- Python 3.12 + `anthropic` + `pydantic`（已装）
- 鉴权：`ANTHROPIC_API_KEY`，**或**中转站场景的 `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`（SDK 原生支持，本机为后者）
- `MODEL = "claude-opus-4-8"`（与 agent_lib.py 一致，便于对比）
- 成本：跑一次评测 ≈ 18 次小调用；整个闯关反复跑成本可忽略

### 7.1 实现变更记录

- 2026-10-21：结构化输出不用课程第 7 课的 `messages.parse(output_format=...)`，
  改用**工具调用 + `tool_choice` 强制**（`messages.create(tools=[...], tool_choice=...)`）。
  原因：本机模型走中转站，不支持 `output_format`（实测返回普通文字导致 JSON 解析失败）；
  工具调用是核心 API，中转站普遍支持。pydantic 模型 `Listing` 保留，改为客户端校验。
  **注意：课程 `07_eval.py` 的 Part A 在本机也会遇到同样的 `ValidationError`**，
  遇到时用同样的思路改（或换支持 output_format 的官方端点）。

## 8. 验收（对我——建项目的人）

- [x] `python eval.py` 端到端跑通，报告三种输出齐全（2026-10-21 实测通过）
- [x] 基线分数：实测 **87%**（78/90），**高于**预设 55%~75% 区间 → 偏差记录见 8.1
- [x] 第 2 关理论可达：仅修朝向约定即可到 98%（10 个朝向错题全修对）

### 8.1 基线偏差记录（2026-10-21）

- **现象**：户型/面积/月租三项基线即 100%，仅朝向 44%、车位 89% 失分。
- **原因**：opus 级模型 + 强类型 schema 把 3 个坑提前填掉了——schema 里
  area/price 声明为 number，"89平米"这类错误根本发生不了（这正是
  extractor.py 注释里写的"schema 也是一种提示词工程"，已转化为第 1 关的教学点）。
- **验收标准修订**：基线显著低于 95% **且至少一个字段 ≤60%**（本实测：朝向 44%）。
  不再硬凑 55~75% 总分区间——为凑分数故意恶化用例/提示词会伤害学习设计。
- **验收过程中修掉的两个工程 bug**（本身就是第 7 课"判分器必须先可靠"的活教材）：
  1. `field_ok` 原写法把"期望 None 实际 None"判错 → 改为双 None 判对、
     单边 None 判错；API 失败的用例改为整条记错（防止全 None 白捡分）
  2. 本机中转站不严格执行 `tool_choice` 强制 → `extract_listing` 增加
     "追问一次"兜底（见 §7.1）
